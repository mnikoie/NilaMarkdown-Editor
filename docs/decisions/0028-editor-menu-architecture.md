# ۰۰۲۸ — معماریِ منوها، نقش‌های ARIA و جداسازیِ popoverها

- **تاریخ:** ۱۴۰۵/۰۵/۳۰
- **وضعیت:** پذیرفته‌شده

## زمینه

ویرایشگر پنج منوی الهام‌گرفته از Typora دارد: `File`، `Edit`،
`Paragraph`، `Format` و `View`. این‌ها از نظر ظاهر کنار هم‌اند، اما یکسان
نیستند:

- بعضی گزینه‌ها یک `Command` همگامِ ProseMirror هستند؛
- بعضی‌ها حالتِ React یا پوستهٔ میزبان را عوض می‌کنند؛
- بعضی‌ها پیش از اجرا به ورودیِ کاربر نیاز دارند؛
- و بخشی از فرمان‌های Typora مثل Recent، File Tree، Preferences و
  Always on Top اصلاً متعلق به کامپوننت نیستند.

دو محدودیت نیز مهم بود. نخست، کلیک روی منو نباید انتخابِ فعلیِ متن را از
بین ببرد؛ فرمان‌هایی مثل لینک یا قالب‌بندی دقیقاً به همان انتخاب وابسته‌اند.
دوم، استفاده از نقش‌های ARIA نباید فقط ظاهری باشد: اگر `menubar` اعلام
کنیم، باید قرارداد کاملِ پیمایشِ کلیدیِ آن را هم پیاده کنیم.

## تصمیم

### ۱. الگوی منو و زیرمنو

هر منو یک کامپوننتِ React مستقل است و دادهٔ فرمان‌های خودش را به شکلِ
آرایه‌ای از `Action` و `Submenu` نگه می‌دارد. هر `Action` می‌تواند این
اطلاعات را داشته باشد:

| فیلد | کاربرد |
|---|---|
| `id` | کلیدِ پایدار برای React و حالتِ زیرمنو |
| `label` / `shortcut` | متنِ دیداری و راهنمای میان‌بر |
| `command` | فرمانِ ProseMirror |
| `run` | callback مربوط به React، مرورگر یا میزبان |
| `enabled` / `checked` | محاسبهٔ وضعیت از روی EditorView |
| `separatorBefore` | مرزبندیِ معناییِ گروه‌ها |

پیش از اجرای `Command`، همان فرمان با `dispatch = undefined` پرس‌وجو
می‌شود. اگر قابلِ اجرا نبود، دکمه غیرفعال می‌ماند؛ اگر بود، بار دوم با
`view.dispatch` اجرا می‌شود. پس منو منطقِ امکان‌پذیریِ فرمان را دوباره
اختراع نمی‌کند.

بازبودنِ منو و شناسهٔ زیرمنوی باز، حالتِ محلیِ همان کامپوننت است. در هر
لحظه فقط یک زیرمنو باز می‌شود و کلیک بیرون، منو و زیرمنو را با هم می‌بندد.
زیرمنو داخلِ پنلِ والد رندر می‌شود، نه در Portal. این انتخاب برای این
نسخه ساده‌تر، قابل‌پیش‌بینی‌تر در RTL و بی‌نیاز از وابستگیِ تازه است.

روی گزینه‌ها `mousedown.preventDefault()` اجرا می‌شود تا مرورگر پیش از
فرمان، فوکوس و انتخابِ ProseMirror را به دکمه منتقل نکند. پس از اجرای
فرمان‌های وابسته به `EditorView`، منو بسته می‌شود و فوکوس به ویرایشگر
برمی‌گردد؛ `FileMenu` که عملیاتِ سند را به callbackهای میزبان می‌سپارد
به‌زور فوکوس را عوض نمی‌کند.

پنج منو ظاهر و کلاس‌های CSS مشترک دارند، ولی یک «موتور منوی عمومی» و
بزرگ ساخته نمی‌شود. نوعِ callbackها و شرط‌های هر منو متفاوت است و انتزاعِ
زودهنگام فقط API را پیچیده می‌کرد. تکرارِ کوچکِ پوسته فعلاً پذیرفته است.

### ۲. نقش‌های ARIA

نگاشتِ نقش‌ها این است:

| عنصر | نقش/صفت |
|---|---|
| دکمهٔ بازکننده | عنصر واقعی `button` با `aria-haspopup="menu"` و `aria-expanded` |
| پنلِ منو یا زیرمنو | `role="menu"` و نامِ قابل‌دسترسی |
| فرمانِ معمولی | `role="menuitem"` |
| فرمانِ روشن/خاموش | `role="menuitemcheckbox"` و `aria-checked` |
| مرزِ گروه | `role="separator"` |
| والدِ زیرمنو | `role="menuitem"` با `aria-haspopup="menu"` و `aria-expanded` |

برای حالت‌های روشن/خاموش از `menuitemcheckbox` استفاده می‌شود، نه صرفاً
آیکونِ تیک؛ در نتیجه صفحه‌خوان وضعیت را مستقل از CSS می‌شنود. غیرفعال‌بودن
نیز با صفتِ واقعیِ `disabled` روی `button` اعلام می‌شود.

ردیفِ بالایی عمداً `role="menubar"` ندارد. این ردیف مجموعه‌ای اختیاری از
کنترل‌های قابلِ جابه‌جایی است و فعلاً قرارداد کاملِ menubar—پیمایش با
ArrowLeft/ArrowRight، roving tabindex و بازکردن با ArrowDown—را ندارد.
اعلامِ نقشِ کامل بدون اجرای رفتارِ کامل، اطلاعاتِ نادرست به فناوریِ کمکی
می‌دهد. هر منو با Tab و دکمه‌های واقعی قابلِ دسترسی است؛ اگر بعداً پیمایشِ
کامل menubar اضافه شود، باید هم‌زمان نقش، مدیریتِ فوکوس و تست‌های کیبوردی
اضافه شوند.

### ۳. چرا popoverها جدا از منو هستند

منو برای **انتخاب یک فرمان** است، نه ورودِ چند فیلد. درج یا ویرایشِ لینک،
تصویر و لینکِ مرجعی به فرم، اعتبارسنجی، Submit/Cancel و مدیریتِ فوکوس نیاز
دارند. بنابراین `LinkPopover`، `ImagePopover` و
`ReferenceLinkPopover` کامپوننت‌های جدا هستند.

گزینهٔ منو فقط callback مربوط را صدا می‌زند و بسته می‌شود؛ سپس popover در
سطحِ `MarkdownEditor` باز می‌شود. این جداسازی چهار نتیجه دارد:

1. فرم داخلِ `role="menu"` قرار نمی‌گیرد و مدلِ تعاملیِ menu با textbox
   و Tabهای فرم مخلوط نمی‌شود؛
2. همان popover از نوارِ سریع، میان‌بر یا چیدمانِ سفارشیِ میزبان هم قابلِ
   فراخوانی است؛
3. بسته‌شدن یا رندرِ دوبارهٔ منو، state و اعتبارسنجیِ فرم را نابود نمی‌کند؛
4. منوهای exportشده به محلِ قرارگیریِ popover وابسته نمی‌شوند و میزبان
   می‌تواند هرکدام را جدا بچیند.

انتخابِ متن در `EditorView` باقی می‌ماند و popover هنگام ثبت، فرمان را روی
همان state اجرا می‌کند. منو مسئولِ نگهداریِ مقدارِ فیلدها یا ساختنِ لینک
و تصویر نیست.

## گزینه‌های دیگر

| گزینه | مزیت | چرا رد شد |
|---|---|---|
| یک کامپوننتِ عمومی و schema‌محور برای هر پنج منو | حذفِ تکرارِ JSX | تفاوتِ زیادِ callbackها، stateها و فرمان‌ها API را مبهم و سخت‌تایپ می‌کرد |
| کتابخانهٔ آمادهٔ Menu/Popover | مدیریتِ focus و collision آماده | وابستگیِ تازه، افزایشِ باندل و نیاز به تصمیمِ فناوری؛ کنترل RTL و انتخابِ ProseMirror نیز باید دوباره آزموده می‌شد |
| Portal برای همهٔ زیرمنوها | فرار از clipping والد | محاسبهٔ موقعیت و بستن هنگام scroll/resize پیچیده‌تر می‌شد و برای چیدمانِ فعلی ضرورتی نداشت |
| قرار دادن فرمِ لینک/تصویر داخلِ منو | یک سطحِ UI کمتر | نقش‌های menu و form، پیمایشِ Tab، فوکوس و چرخهٔ بسته‌شدن با هم تداخل پیدا می‌کردند |
| `role="menubar"` روی ردیفِ بالا | شباهتِ اسمی به برنامهٔ دسکتاپ | بدونِ پیاده‌سازیِ کاملِ arrow navigation و roving tabindex ادعای ARIA نادرست بود |
| نگه‌داشتنِ popover داخلِ هر منو | هم‌مکانیِ کد | استفادهٔ مجدد از toolbar/shortcut را سخت و state فرم را به عمرِ منو وابسته می‌کرد |

## پیامدها

- منوها بدون وابستگیِ تازه و با API جداگانه export می‌شوند؛ میزبان می‌تواند
  نمونهٔ داخلی را خاموش و در چیدمانِ خودش استفاده کند.
- فرمان‌های مخصوص پوستهٔ دسکتاپ یا حذف شده‌اند یا فقط با callback میزبان
  ظاهر می‌شوند؛ کامپوننت ادعای مالکیتِ فایل‌سیستم و پنجرهٔ برنامه را ندارد.
- تست‌های e2e باید علاوه بر نتیجهٔ فرمان، نقش‌های `menu`، `menuitem` و
  `menuitemcheckbox` و بازشدنِ زیرمنوها را نیز بررسی کنند.
- مقداری تکرار میانِ پنج کامپوننت باقی می‌ماند. اگر رفتار مشترک بزرگ‌تر شد،
  می‌توان فقط پوستهٔ اثبات‌شده را استخراج کرد، بدونِ یکی‌کردنِ مدلِ دادهٔ
  همهٔ منوها.
- زیرمنوی inline ممکن است در میزبانی با `overflow: hidden` بریده شود. اگر
  این مسئله در محصول واقعی رخ داد، Portal و الگوریتمِ موقعیت‌یابی با یک
  تصمیمِ تازه بررسی می‌شود.
- افزودنِ `menubar` در آینده یک تغییرِ صرفاً ظاهری نیست؛ مدیریتِ فوکوس،
  کلیدهای جهت و تستِ صفحه‌خوان بخشی از همان تغییر خواهند بود.
