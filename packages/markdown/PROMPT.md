# پرامپتِ ساختِ `@tamin/markdown`

> این سند برای کسی نوشته شده که قرار است این پکیج را بسازد — چه آدم، چه
> عاملِ هوش مصنوعی. هدفش این است که تصمیم‌های سخت **از قبل** گرفته شده باشند
> و سازنده مجبور نشود وسطِ کار حدس بزند.
>
> نسخهٔ سند: ۱ — ۳۰ مرداد ۱۴۰۵

---

## ۱. چه چیزی ساخته می‌شود

یک ویرایشگر و نمایشگرِ Markdown برای React، با تجربهٔ کاربریِ
[Typora](https://typora.io/).

آنچه Typora را Typora می‌کند و باید تکرار شود:

> **پیش‌نمایشِ زنده، بدونِ دو ستون.** ستونِ کد و ستونِ خروجی وجود ندارد. همان‌جا
> که تایپ می‌کنی رندر می‌شود، و نشانه‌های Markdown (`**`، `#`، `` ` ``) فقط
> وقتی پیدا می‌شوند که مکان‌نما داخلِ همان بلوک برود. مکان‌نما که بیرون رفت،
> دوباره پنهان می‌شوند.

اگر این یک ویژگی درست پیاده نشود، بقیه‌اش بی‌معنی است. هر تصمیمِ دیگری در این
سند در خدمتِ همین است.

### دو نقطهٔ ورود

```ts
import { MarkdownEditor } from "@tamin/markdown";        // ویرایشگرِ کامل
import { MarkdownViewer } from "@tamin/markdown/viewer";  // فقط نمایش
```

`viewer` باید **مستقل** باشد: کسی که فقط نمایش می‌خواهد نباید یک بایت از کدِ
ویرایش را دانلود کند. این با `exports` و بیلدِ چند-ورودی به دست می‌آید، نه با
یک `if` داخلِ کامپوننت.

بودجهٔ حجم (gzip، بی‌احتسابِ React):

| ورودی | سقف |
|---|---|
| `@tamin/markdown/viewer` | ۴۰ کیلوبایت |
| `@tamin/markdown` | ۱۵۰ کیلوبایت |
| KaTeX و Mermaid و Shiki | خارج از این عدد — با `import()` تنبل بار می‌شوند |

## ۲. تصمیم‌هایی که گرفته شده‌اند

این‌ها بحث‌شده‌اند و **باز نیستند**. اگر سازنده با یکی مخالف است، اول بحث کند،
نه اینکه در حینِ کار عوضش کند.

### موتور: ProseMirror + remark

| | |
|---|---|
| مدلِ سند | ProseMirror — سند یک **درخت** است، نه رشتهٔ متن |
| خواندن و نوشتنِ Markdown | remark/mdast |
| پل بینِ این دو | خودمان می‌نویسیم (بخش ۵) |

**چرا ProseMirror:** پیش‌نمایشِ زنده یعنی ویرایشگر باید بداند مکان‌نما داخلِ
کدام گره از سند است. با یک ویرایشگرِ متنی این را فقط می‌شود شبیه‌سازی کرد و
همیشه لبه‌هایی می‌ماند که غلط رفتار می‌کنند. ProseMirror از پایه سند-محور است.

**چرا remark و نه `prosemirror-markdown`:** بستهٔ رسمیِ `prosemirror-markdown`
روی `markdown-it` بنا شده و افزونه‌هایش محدودند. remark برای GFM و ریاضی و
front matter افزونهٔ پخته دارد و همان درختِ mdast را می‌دهد که برای viewer هم
لازم داریم. هزینه‌اش این است که پلِ mdast↔ProseMirror را باید خودمان بنویسیم —
که در بخش ۵ دقیقاً مشخص شده.

### فقط React، ولی مستقل از Next

`react` و `react-dom` در `peerDependencies` با `>=18`. هیچ `import` از `next/*`
مجاز نیست. باید در Vite و CRA و Next یکسان کار کند.

هر فایلی که ویرایشگر را رندر می‌کند `"use client"` می‌خواهد — ولی این وظیفهٔ
**مصرف‌کننده** است، نه ما. در README بنویس.

### استایل: Tailwind برای نوشتن، CSS برای انتشار

داخلِ پکیج با Tailwind 4 می‌نویسی. بیلد یک `dist/styles.css`ِ کامپایل‌شده
می‌سازد. مصرف‌کننده فقط این را import می‌کند:

```ts
import "@tamin/markdown/styles.css";
```

و **لازم نیست Tailwind داشته باشد**. این تنها راهی است که هم راحتیِ نوشتن را
داشته باشی هم پکیجی که همه‌جا نصب می‌شود.

سه شرط:

1. همهٔ کلاس‌ها با `tm-` پیشوند بگیرند (`prefix` در کانفیگِ Tailwind) تا با
   Tailwindِ خودِ مصرف‌کننده تصادم نکنند.
2. هیچ ریست یا `preflight`ی منتشر نشود — استایلِ صفحهٔ میزبان را خراب می‌کند.
3. رنگ‌ها و فاصله‌ها همه از **CSS variables** بیایند (بخش ۹)، وگرنه تمِ
   سفارشی ممکن نمی‌شود.

## ۵. پلِ mdast ↔ ProseMirror

این بخشِ اصلیِ کار است و باید **اول** نوشته شود، قبل از هر UI.

### جدولِ نگاشت

| mdast | گرهٔ ProseMirror | نکته |
|---|---|---|
| `root` | `doc` | |
| `paragraph` | `paragraph` | |
| `heading` | `heading` با `attrs.level` | ۱ تا ۶ |
| `text` | متن | |
| `strong` | نشانهٔ `strong` | |
| `emphasis` | نشانهٔ `em` | |
| `delete` | نشانهٔ `strike` | GFM |
| `inlineCode` | نشانهٔ `code` | |
| `link` | نشانهٔ `link` با `href` و `title` | |
| `image` | گرهٔ درون‌خطیِ `image` | |
| `list` + `listItem` | `bullet_list` / `ordered_list` + `list_item` | |
| `listItem.checked` | `attrs.checked` روی `list_item` | چک‌لیستِ GFM |
| `blockquote` | `blockquote` | |
| `code` | `code_block` با `attrs.language` | |
| `thematicBreak` | `horizontal_rule` | |
| `table` و زیرمجموعه‌اش | گره‌های `prosemirror-tables` | `attrs.align` را نگه دار |
| `math` / `inlineMath` | `math_block` / `math_inline` | از `remark-math` |
| `footnoteDefinition` و `footnoteReference` | گره‌های خودشان | |
| `yaml` | `front_matter` — یک گره در ابتدای سند | |
| `html` | `html_block` — دست‌نخورده نگه دار | بخش ۱۱ |

### شرطی که باید همیشه برقرار باشد

**رفت و برگشت باید بی‌تغییر باشد.** هر سندی که وارد شود و بی‌ویرایش خارج شود،
باید بایت‌به‌بایت همان باشد:

```ts
serialize(parse(md)) === md
```

این را به‌صورتِ تستِ ویژگی (property test) بنویس، نه چند نمونهٔ دستی:

```ts
// tests/unit/roundtrip.test.ts
// کاربر فایلش را باز می‌کند، یک حرف عوض می‌کند، ذخیره می‌کند — و اگر این
// شرط برقرار نباشد، diff پر می‌شود از تغییرهایی که او نداده.
for (const sample of fixtures) {
  expect(serialize(parse(sample))).toBe(sample);
}
```

`fixtures` باید حداقل این‌ها را داشته باشد: هر ردیفِ جدولِ بالا، سندِ تودرتو
(نقلِ‌قول داخلِ فهرست داخلِ نقلِ‌قول)، جدولِ با سلولِ خالی، کدِ داخلِ فهرست،
HTML خام، متنِ فارسی و مخلوطِ فارسی-انگلیسی، ایموجی و کاراکترهای خارج از BMP.

جاهایی که Markdown چند نوشتنِ معادل دارد (`*` یا `-` برای فهرست، `_` یا `*`
برای تأکید)، انتخابِ خودت را در `remark-stringify` **ثابت** کن و در README
بنویس. سکوت دربارهٔ این یعنی diffهای غافلگیرکننده.

## ۶. پیش‌نمایشِ زنده — قلبِ کار

### رفتارِ مطلوب

مکان‌مان **بیرونِ** بلوک:

```
سلام دنیا            ← «دنیا» پررنگ دیده می‌شود، ** دیده نمی‌شود
```

مکان‌نما **داخلِ** بلوک:

```
سلام **دنیا**        ← ستاره‌ها پیدا می‌شوند و قابلِ ویرایش‌اند
```

### پیاده‌سازی

یک افزونهٔ ProseMirror که با `Decoration` کار می‌کند:

```ts
// src/core/plugins/live-preview.ts
//
// چرا Decoration و نه تغییرِ سند: نشانه‌های Markdown **بخشی از سند نیستند**.
// اگر داخلِ سند بگذاریشان، در خروجی هم می‌آیند و رفت‌وبرگشت می‌شکند. پس
// لایه‌ای رویِ نمایش‌اند که با حرکتِ مکان‌نما عوض می‌شود.
new Plugin({
  props: {
    decorations(state) {
      const { from, to } = state.selection;
      // گره‌هایی که مکان‌نما داخلشان است → نشانه‌ها آشکار
      // بقیه → نشانه‌ها با CSS پنهان (display:none، نه حذف)
    },
  },
});
```

### پنج حالتی که معمولاً فراموش می‌شوند

اگر این‌ها را زود تست نکنی، دیر پیدایشان می‌کنی:

1. **انتخابِ چندبلوکی.** کاربر سه پاراگراف را انتخاب کرده. کدامشان نشانه نشان
   می‌دهند؟ (پیشنهاد: هیچ‌کدام — وگرنه صفحه می‌لرزد.)
2. **گره‌های تودرتو.** تأکید داخلِ لینک داخلِ عنوان.
3. **پرشِ چیدمان.** پیداشدنِ `**` عرض را عوض می‌کند و متن جابه‌جا می‌شود.
   با `font-variant-numeric` و عرضِ ثابتِ نشانه‌ها کمش کن، یا نشانه‌ها را
   `position: absolute` کن.
4. **کلیک روی متنِ رندرشده.** مکان‌نما باید در جای درستِ متنِ خام بنشیند —
   نه اولِ بلوک.
5. **Undo.** برگشت نباید حالتِ نمایش را با حالتِ سند قاطی کند.

### حالتِ سورس

یک کلید (`Ctrl+/`) که کلِ سند را به متنِ خامِ Markdown عوض می‌کند و برمی‌گرداند.
اینجا CodeMirror لازم نیست؛ یک `textarea` با فونتِ mono کافی است. مهم این است
که موقعِ برگشت، **موقعیتِ مکان‌نما حفظ شود**.

```ts
  openLinksInNewTab?: boolean;
  /** تبدیلِ نشانیِ تصویرهای نسبی به مطلق. */
  resolveImageSrc?: (src: string) => string;
  className?: string;
}
```

### دو قاعدهٔ رفتاری

**`onChange` نباید در هر ضربهٔ کلید صدا شود.** پیش‌فرضِ ۳۰۰ میلی‌ثانیه. سریالایز
کردنِ سندِ بزرگ ارزان نیست و در فایلِ چندهزارخطی تایپ را کند می‌کند.

**در حالتِ کنترل‌شده، `value`ی که خودت تولید کرده‌ای نباید سند را بازسازی کند.**
وگرنه مکان‌نما با هر حرف به اولِ سند می‌پرد. مقدارِ آخرینِ سریالایزشده را نگه
دار و اگر `value` با آن یکی بود، دست به سند نزن.

## ۱۰. فارسی و راست‌به‌چپ

**اینجا جایی است که می‌توانی از Typora جلو بزنی** — پشتیبانیِ RTLِ خودش ضعیف
است. این را جدی بگیر، نه به‌عنوانِ ویژگیِ جانبی.

| نیاز | راه |
|---|---|
| جهتِ کلِ سند | `dir` prop |
| تشخیصِ خودکار | `dir="auto"` از رویِ اولین کاراکترِ قویِ هر بلوک |
| جهتِ هر بلوک جدا | هر بلوک `dir` خودش را بگیرد — پاراگرافِ فارسی کنارِ انگلیسی |
| کدِ داخلِ متنِ فارسی | بلوکِ کد **همیشه** LTR، حتی در سندِ RTL |
| نشانه‌های Markdown | `**` و `#` نباید در RTL جابه‌جا دیده شوند |
| اعداد | نگاشتِ اختیاریِ ۰۱۲۳ ↔ 0123 |
| نویسه‌های نامرئی | ZWNJ (نیم‌فاصله) نباید در رفت‌وبرگشت گم شود |
| کلیدِ نیم‌فاصله | `Shift+Space` → `‌` |
| جدول | ترتیبِ ستون‌ها در RTL برعکس شود |
| فونت | پیش‌فرضِ فارسی: Vazirmatn با fallback به system-ui |

آن ردیفِ ZWNJ را حتماً تست کن. «می‌شود» با نیم‌فاصله و «می شود» با فاصله دو
چیزِ متفاوت‌اند و اگر سریالایزر نیم‌فاصله را عادی‌سازی کند، متنِ کاربر خراب
می‌شود.

## ۱۱. امنیت

Markdown می‌تواند HTML خام داشته باشد. اگر محتوا از کاربرِ دیگری بیاید، این
یعنی XSS.

```ts
interface Props {
  /**
   * "escape"  — HTML به‌صورتِ متن نشان داده شود (پیش‌فرض؛ امن)
   * "sanitize" — رندر شود ولی از فهرستِ سفید عبور کند
   * "raw"     — بی‌فیلتر. فقط وقتی محتوا مالِ خودت است.
   */
  html?: "escape" | "sanitize" | "raw";
}
```

پیش‌فرض `"escape"` است. حالتِ ناامن باید **انتخابِ صریح** باشد، نه پیش‌فرض.

سه چیزِ دیگر:

- `javascript:` و `data:` در `href` مسدود شوند (به‌جز `data:image/*` در `src`).
- لینکِ خارجی: `rel="noopener noreferrer"`.
- Mermaid کدِ دلخواه اجرا می‌کند. `securityLevel: "strict"` بگذار و اگر
  محتوا از بیرون می‌آید، پیش‌فرض خاموشش کن.

## ۱۸. مارک‌های سفارشی و ارجاعِ بین‌سندی

> این بخش بعد از کار روی اسنادِ واقعیِ بخشنامه اضافه شد. نیازِ واقعی است، نه فرضی.

### ۱۸-۱. مکانیزم: directive

کاربر باید بتواند **مارکِ خودش** را تعریف کند. نحوِ ثابتِ این کار `remark-directive`
است (پیشنهادِ عمومیِ CommonMark) — نه براکتِ دست‌ساز:

```markdown
:::note{نوع=compiler}          بلوکی (container)
محتوا
:::

:ref[متنِ نمایشی]{نوع=آیین‌نامه مصوب=۱۳۵۵/۱۰/۲۵}    درون‌خطی (text)
```

**چرا این و نه `[Note-Compiler]`:** براکتِ خام در مارک‌داون یعنی *link reference*.
پارسر آن را لینکِ خراب می‌بیند و متن را عیناً چاپ می‌کند. directive یک گرهٔ واقعیِ
mdast است: اسم دارد، صفت دارد، و در جدولِ نگاشتِ بخش ۵ جا می‌گیرد.

مزیتِ اصلی: **مکانیزم عمومی است.** ادیتور یک‌بار directive را می‌فهمد، هر مارکِ
سفارشیِ بعدی مجانی کار می‌کند.

```ts
interface MarkdownEditorProps {
  /** مارک‌های سفارشیِ کاربر. کلید = نامِ directive. */
  directives?: Record<string, {
    نوع: "بلوکی" | "درون‌خطی" | "برگی";
    صفات?: string[];              // صفاتِ مجاز؛ ناشناخته → هشدار نه خطا
    render?: (node) => ReactNode;  // نبود = رندرِ پیش‌فرضِ عمومی
  }>;
}
```

**قاعده:** directiveِ ناشناخته هرگز خطا نمی‌دهد و هرگز حذف نمی‌شود — خام نمایش
داده می‌شود. سندِ کاربر با نصب‌نبودنِ یک افزونه نباید بشکند.

### ۱۸-۲. ارجاع، لنگر و شناسه

هر سرفصل لنگرِ پایدار می‌گیرد؛ هر ارجاع به لنگر اشاره می‌کند، نه به متن:

```markdown
# فصل چهارم: نحوه ارزیابی {#fasl-4}

:ref[فصل چهارم این بخشنامه]{هدف=62285360#fasl-4}
:ref[ماده ۵۰ قانون تأمین اجتماعی]{هدف=قانون-تامین#ماده-۵۰}
```

`هدف` = `<شناسهٔ سند>#<لنگر>`. بدونِ آن، ارجاع فقط رشتهٔ متن است و نه کلیک
می‌شود، نه resolve.

### ۱۸-۳. ★ هشدارِ ارجاعِ شکسته هنگامِ تغییرِ نام

**این مهم‌ترین بندِ این بخش است.**

وقتی کاربر عنوان یا شناسهٔ سندی را عوض می‌کند، ادیتور باید **پیش از ثبت**، ارجاع‌های
واردشونده را پیدا کند و بپرسد:

```
┌────────────────────────────────────────────────┐
│  ⚠  این بخشنامه در ۴ جای دیگر ارجاع خورده      │
│                                                │
│   • بخشنامه ۶۲۲۸۵۳۶۰ — فصل دوم، بند ۱۴        │
│   • بخشنامه ۶۲۲۸۵۳۶۰ — فصل دوم، بند ۱۹        │
│   • بخشنامه ۴۳۸۹۱۹۳۶ — فصل اول، بند ۳         │
│   • خلاصهٔ یک‌نگاهی ۶۲۲۸۵۳۶۰                    │
│                                                │
│   [ همه را اصلاح کن ]  [ فقط این را ]  [ لغو ] │
└────────────────────────────────────────────────┘
```

قاعده‌ها:

- ارجاع‌ها **پیش از** نوشتنِ تغییر شمرده می‌شوند. اگر بعد از ثبت بپرسی، دیر است.
- «همه را اصلاح کن» باید **یک قدمِ undo** باشد، نه ۴ قدم.
- سندی که قابلِ نوشتن نیست (فقط‌خواندنی، قفل، خارج از workspace) در فهرست
  می‌آید ولی با علامتِ «اصلاح‌ناپذیر» — و کاربر آگاه می‌شود، نه اینکه بی‌صدا رد شود.
- اگر ارجاعی به هدفِ ناموجود اشاره کند = **«رفرنسِ گمشده»**. حذف نمی‌شود؛ در پنلِ
  جداگانه فهرست می‌شود. سه حالت داریم: سالم / گمشده / **نامعلوم** (سند هنوز
  ایندکس نشده). «نامعلوم» هرگز به «گمشده» ترجمه نمی‌شود.

```ts
interface MarkdownEditorProps {
  /** فهرستِ ارجاع‌های واردشونده به یک هدف. */
  resolveBacklinks?: (هدف: string) => Promise<Backlink[]>;
  /** پیش از تغییرِ نام صدا می‌شود. false برگردان تا لغو شود. */
  onRename?: (از: string, به: string, ارجاعات: Backlink[])
    => Promise<boolean | "همه" | "فقط-این">;
}
```

### ۱۸-۴. چه چیزی حتماً تست شود

- directiveِ ناشناخته → خام نمایش داده شود، نه خطا، نه حذف.
- `serialize(parse(md)) === md` برای هر سه نوعِ directive (بخش ۵ نقض نشود).
- directive داخلِ بندِ تورفتهٔ فهرست — رفت‌وبرگشت سالم بماند.
- تغییرِ نام با ۰، ۱ و ۱۰ ارجاعِ واردشونده.
- «همه را اصلاح کن» سپس undo → همه با یک قدم برگردند.
- ارجاع به سندِ فقط‌خواندنی → علامتِ اصلاح‌ناپذیر، نه شکستِ بی‌صدا.
- هدفِ ناموجود → «گمشده»، و سندِ ایندکس‌نشده → «نامعلوم». این دو قاطی نشوند.
